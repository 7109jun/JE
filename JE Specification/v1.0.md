# JE Specification v1.0

**JE — Just Executable**

> Version: 1.0
> Format Extension: `.jxj`
> Magic Signature: `[ JE : O]`

---

## 1. Introduction

JE (Just Executable) is a **text-based executable file format**.

JE is designed to preserve the structural concepts of existing executable formats while allowing executable files to be represented as text.

JE files can be read and edited by humans and executed through the JE runtime.

The standard file extension is:

```text
.jxj
```

A file without an extension can also be identified as a JE file when it begins with the following JE Magic Signature:

```text
[ JE : O]
```

---

# 2. Design Goals

The primary goals of JE are:

1. Executable files should be representable as text.
2. JE files should be readable and editable by humans.
3. JE should function as an executable file format.
4. JE should provide an executable structure similar to PE.
5. PE ↔ JE conversion should be supported.
6. Invalid files should be safely rejected.
7. Memory and file boundaries should always be validated during execution and parsing.
8. Native process execution should be supported on Windows.

---

# 3. File Identification

## 3.1 Standard Extension

The standard JE extension is:

```text
.jxj
```

The extension is case-insensitive.

Examples:

```text
program.jxj
PROGRAM.JXJ
Program.JxJ
```

All of these may be recognized as JE files.

## 3.2 Magic Signature

JE uses the following Magic Signature:

```text
[ JE : O]
```

The exact Magic Signature length is 9 bytes.

```text
JE_MAGIC_LEN = 9
```

The Magic Signature must appear at the beginning of the file.

Example:

```text
[ JE : O]

AUTHOR = "Example"
FORMAT = "JE"
VERSION = 1
ARCH = X86_64
```

## 3.3 Extensionless Files

A file without an extension may still be detected as JE when it begins with the JE Magic Signature.

Example:

```text
hello
```

File contents:

```text
[ JE : O]

...
```

---

# 4. Character Encoding

The JE text area uses UTF-8 as its default encoding.

An implementation must not treat invalid UTF-8 input as valid JE text.

Text data must be checked to ensure that access remains within the file boundaries.

---

# 5. File Structure

A typical JE file has the following structure:

```text
[ JE : O]

AUTHOR = "..."
FORMAT = "JE"
VERSION = 1
ARCH = X86_64

SYSTEM {
    ENTRY = main
    SUBSYSTEM = CONSOLE
}

SECTION .text {
    ...
}

CODE {
    ...
}
```

A JE file is logically composed of:

```text
Magic
Header
System Information
Sections
Code
Optional Data
```

---

# 6. Header

The JE Header defines basic file metadata.

The standard fields are:

```text
AUTHOR
FORMAT
VERSION
ARCH
```

## 6.1 AUTHOR

Specifies the author or creator.

Syntax:

```text
AUTHOR = "text"
```

Example:

```text
AUTHOR = "JE"
```

## 6.2 FORMAT

Specifies the file format.

Syntax:

```text
FORMAT = "JE"
```

The standard format value is:

```text
JE
```

Other values must not be treated as a valid JE format.

## 6.3 VERSION

Specifies the JE format version.

Syntax:

```text
VERSION = integer
```

Example:

```text
VERSION = 1
```

Values that cannot be interpreted as valid integers must not be accepted as a valid VERSION field.

## 6.4 ARCH

Specifies the target architecture.

Examples:

```text
ARCH = X86
ARCH = X86_64
ARCH = ARM
ARCH = ARM64
```

An implementation must reject architecture values that it does not support.

---

# 7. SYSTEM Block

The SYSTEM Block defines system-level execution information.

Example:

```text
SYSTEM {
    ENTRY = main
    SUBSYSTEM = CONSOLE
}
```

## 7.1 ENTRY

Specifies the label where execution begins.

Example:

```text
ENTRY = main
```

If the specified label does not exist, execution must not begin.

## 7.2 SUBSYSTEM

Specifies the execution environment used by the program.

Example:

```text
SUBSYSTEM = CONSOLE
```

An implementation may reject unsupported subsystems before execution.

---

# 8. Sections

JE may use a section system similar to PE.

Common sections include:

```text
.text
.rdata
.data
.bss
```

Sections are used to logically separate code and data.

Example:

```text
SECTION .text {
    ...
}
```

Section names must be validated according to the implementation's section rules.

Any access to file data must remain within the actual file boundaries.

---

# 9. CODE Block

The CODE Block contains JE executable code.

Syntax:

```text
CODE {
    ...
}
```

Example:

```text
CODE {
    main:
        MOV R0, 40
        ADD R0, 2
        PRINT R0
        EXIT 0
}
```

The CODE Block must be enclosed in braces.

Braces inside strings must not be interpreted as actual block delimiters.

---

# 10. Labels

A label identifies a specific location in the code.

Syntax:

```text
name:
```

Example:

```text
main:
    MOV R0, 1

loop:
    ADD R0, 1
    JMP loop
```

A label must not be defined more than once within the same CODE Block.

A program containing duplicate labels is invalid.

---

# 11. Registers

The JE execution environment provides eight general-purpose registers:

```text
R0
R1
R2
R3
R4
R5
R6
R7
```

Each register stores a 64-bit integer value.

Example:

```text
MOV R0, 100
MOV R1, R0
```

---

# 12. Instruction Set

## 12.1 Data Movement

```text
MOV destination, source
```

Example:

```text
MOV R0, 10
MOV R1, R0
```

---

## 12.2 Arithmetic

```text
ADD destination, source
SUB destination, source
```

Example:

```text
ADD R0, 5
SUB R0, 2
```

---

## 12.3 Bitwise Operations

```text
XOR destination, source
AND destination, source
OR  destination, source
```

---

## 12.4 Shift Operations

```text
SHL destination, count
SHR destination, count
```

---

## 12.5 Increment / Decrement

```text
INC register
DEC register
```

---

## 12.6 Comparison

```text
CMP left, right
```

CMP updates the execution condition state.

Example:

```text
CMP R0, 0
JZ zero
```

---

## 12.7 Stack

```text
PUSH value
POP register
```

The JE execution environment provides a value stack.

A POP operation on an empty stack must terminate with an execution error.

---

# 13. Control Flow

## 13.1 JMP

Performs an unconditional branch.

```text
JMP label
```

Example:

```text
loop:
    ADD R0, 1
    JMP loop
```

A jump to the same label is valid.

Infinite loops may be controlled by an execution step limit.

---

## 13.2 JZ

Branches when the condition state is zero.

```text
JZ label
```

---

## 13.3 JNZ

Branches when the condition state is not zero.

```text
JNZ label
```

---

# 14. CALL / RET

## 14.1 CALL

Calls a label and stores the current return position on the call stack.

```text
CALL function
```

Example:

```text
CALL sum
```

## 14.2 RET

Returns to the most recently stored call position.

```text
RET
```

A RET operation with an empty call stack must fail.

---

# 15. Input and Output

## 15.1 PRINT

Prints a register or value.

```text
PRINT R0
```

Example:

```text
MOV R0, 42
PRINT R0
```

Output:

```text
42
```

---

# 16. Program Termination

A program can terminate using the `EXIT` instruction.

```text
EXIT code
```

Example:

```text
EXIT 0
```

The exit code must be returned as the program's result code.

The program's exit code must not be confused with an internal JE error status.

---

# 17. Execution Safety

A JE execution engine should provide the following safeguards.

## 17.1 Execution Step Limit

A maximum number of execution steps may be configured to prevent infinite loops and runaway execution.

Example:

```text
step_limit = N
```

When the limit is reached, execution is terminated.

## 17.2 Stack Bounds

The value stack and call stack must not exceed their implementation-defined maximum sizes.

## 17.3 Input Bounds

Every file access must satisfy:

```text
offset < file_size
```

When reading a multi-byte value, the entire accessed range must remain within the file.

## 17.4 Integer Overflow

Integer overflow must not occur during:

* file size calculations
* offset calculations
* memory size calculations
* allocation size calculations

Checked arithmetic should be used.

---

# 18. Comments

JE supports `#` as a comment character.

Example:

```text
MOV R0, 10 # initialize R0
ADD R0, 2  # add two
```

Comments do not affect instruction execution.

A `#` inside a string must not begin a comment.

Example:

```text
AUTHOR = "A # B"
```

---

# 19. Tokenization

The JE parser supports the following basic token types:

```text
IDENTIFIER
STRING
NUMBER
{
}
[
]
=
:
,
NEWLINE
```

Whitespace and line breaks may be ignored according to the grammar rules.

Strings are enclosed in quotation marks.

Example:

```text
"hello"
```

# 21. PE → JE

A PE file may be converted into a JE text representation.

```text
example.exe
     |
     v
   PE → JE
     |
     v
example.jxj
```

The converted JE file may contain structural PE information in textual form.

The original PE bytes may also be preserved inside the JE representation.

Example:

```text
PE_RAW_HEX {
    ...
}
```

This data may be used to reconstruct the original PE during JE → PE conversion.

---

# 22. JE → PE

A JE file may be converted back into a PE file.

```text
example.jxj
     |
     v
   JE → PE
     |
     v
example.exe
```

When `PE_RAW_HEX` is present, the implementation may restore the original PE bytes after validating the hexadecimal data.

Invalid hexadecimal characters or corrupted data must be rejected.

---

# 23. Round-Trip Requirement

The following conversion must be supported:

```text
PE → JE → PE
```

When the original PE data is preserved, the following condition should hold:

```text
original_pe == reconstructed_pe
```

The reconstructed PE must therefore be byte-for-byte identical to the original.

---

# 24. File Validation

A JE validator must check at least:

```text
Magic
UTF-8
Header syntax
FORMAT
VERSION
ARCH
SYSTEM syntax
ENTRY
Block balance
CODE syntax
Duplicate labels
Instruction syntax
Numeric range
```

Invalid input must never be reported as `valid JE`.

---

# 25. Extensionless Validation

A file without an extension may be detected using the JE Magic Signature.

However, it must still pass full JE syntax and structure validation before being considered a complete valid JE program.

A file containing only:

```text
[ JE : O]
```

must not be considered a complete JE executable.

---

# 26. Windows Execution

A Windows implementation may provide native process execution.

The Windows process bridge may use:

```text
CreateProcessA
WaitForSingleObject
GetExitCodeProcess
```

The normal execution flow is:

```text
CreateProcessA
      ↓
WaitForSingleObject
      ↓
GetExitCodeProcess
      ↓
Process Result
```

Process creation failures and the child process's own exit code must be treated as separate concepts.

---

# 27. CLI Reference

The standard CLI commands are:

```text
je detect <file>
je validate <file>
je run <file>
je launch <file>

je pe2je <input.exe> <output.jxj>
je je2pe <input.jxj> <output.exe>
```

## detect

Detects the file type.

```text
je detect program.jxj
```

## validate

Validates the syntax and structure of a JE file.

```text
je validate program.jxj
```

## run

Executes the JE CODE Block using the JE execution engine.

```text
je run program.jxj
```

## launch

Launches a JE or PE program through the native execution path.

```text
je launch program.exe
```

## pe2je

Converts a PE file into JE.

```text
je pe2je program.exe program.jxj
```

## je2pe

Converts a JE file into PE.

```text
je je2pe program.jxj program.exe
```

# 29. Security Requirements

JE parsers and loaders may process untrusted files.

Implementations must therefore follow these principles:

* Validate file offsets.
* Prevent integer overflow in file-size calculations.
* Validate stack bounds.
* Apply reasonable limits to the number of labels.
* Apply reasonable limits to line length.
* Apply a maximum execution step count where appropriate.
* Reject invalid UTF-8.
* Reject invalid PE directories.
* Safely reject malformed relocation, import, and export data.
* Reject malformed hexadecimal data.

# 33. Minimal Valid JE

A minimal valid JE program can be written as:

```text
[ JE : O]

AUTHOR = "Example"
FORMAT = "JE"
VERSION = 1
ARCH = X86_64

SYSTEM {
    ENTRY = main
}

CODE {
    main:
        MOV R0, 42
        PRINT R0
        EXIT 0
}
```

Output:

```text
42
```

---

# 34. Example Program

Example including a function call:

```text
[ JE : O]

AUTHOR = "JE"
FORMAT = "JE"
VERSION = 1
ARCH = X86_64

SYSTEM {
    ENTRY = main
}

CODE {
    main:
        MOV R0, 40
        PUSH R0
        POP R1
        INC R1
        CALL sum_two
        PRINT R0
        EXIT 0

    sum_two:
        ADD R1, 1
        MOV R0, R1
        RET
}
```

Result:

```text
42
```

# 36. Versioning

The JE format version is specified using:

```text
VERSION = 1
```

Changes that are incompatible with the existing syntax or binary representation must use a new JE specification version.

Examples:

```text
JE v1.0
JE v2.0
```

An implementation must not arbitrarily execute an unsupported major version.

---

# 37. Design Philosophy

The central philosophy of JE is:

> **Executable files should not have to be unreadable binary blobs.**

JE aims to represent executable structure as text while retaining important executable properties:

```text
Readable
Executable
Structured
Convertible
Validated
Portable
```

JE is intended to reduce the boundary between human-readable text and executable files.
